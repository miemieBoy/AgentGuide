## 五分钟结论

如果你只想知道「我该用什么」，看这一节。

### 1. 你真正要解决的问题是哪一类？

```
要不要执行 JavaScript？
├─ 不要 → HTTP 客户端（requests / curl / DSH 的 web_fetch）
│         快、便宜、够用；静态页、SSR、API、文章页都归这
└─ 要
   ├─ 要登录态吗？
   │  ├─ 要 → 浏览器 + 复用你已登录的环境（CDP 接管 / 浏览器扩展）
   │  └─ 不要 → 普通浏览器自动化（Playwright / CDP）
   └─ 要批量、要无人值守吗？
      ├─ 要 → 爬虫框架（Scrapling / Scrapy）
      └─ 不要 → 交互式自动化（Playwright MCP / chrome-devtools-mcp）
```

### 2. 三个最容易踩的认知误区

| 误区 | 事实 |
|---|---|
| 「浏览器扩展只能读页面，不能操作」 | **错**。`chrome.debugger` 权限让扩展能拿到接近完整 CDP 的能力，点击、填表、翻页都能做 |
| 「MCP 是某个产品独有的」 | **错**。MCP 是开放协议；同一个服务器可以被 Claude、Cursor、DSH 等任意客户端驱动 |
| 「web_fetch 抓不到会报错」 | **错，而且更危险**。SPA 页面常返回 `200` + 空壳，看着成功其实什么都没拿到 |

### 3. 判断一个工具是否真能干活的唯一方法

**同一条 URL，两个工具各跑一遍，比输出。** 不要看宣传，看返回内容。

本库的实测例子：同一条 SPA 榜单页，`web_fetch` 只拿回一行 `<title>`（HTTP 200，不报错），浏览器方案拿回完整 50 条结构化数据 + 81 条网络请求。

## 核心结论速查

| 场景 | 推荐 | 不推荐 |
|---|---|---|
| 静态页面 / 文章 / API 文档 | `web_fetch`、requests | 开浏览器（慢 100 倍） |
| SPA / 无限滚动 | 浏览器（Playwright / CDP） | 任何纯 HTTP 方案 |
| 需要登录态 | CDP 接管已登录浏览器 / 浏览器扩展 | 另起隔离 profile（没登录态） |
| 批量采集、定时跑 | Scrapling / Scrapy | 手动脚本 |
| 一次性看懂某页面怎么实现 | chrome-devtools-mcp | 爬虫框架（太重） |
| 让 agent 边聊边操作网页 | Playwright MCP / chrome-devtools-mcp | 自己写扩展（成本高） |
